ADR-03: Agentic AI Framework and Orchestration Method

Field Details
Context The multi-agent workflow (Planning, Quality Validation, Market Intelligence, Buyer Matching, Logistics Scheduling) requires secure tool execution, step-by-step reasoning, and transactional coordination without exposing internal tools, database connection secrets, or raw AI ports directly to public web or mobile clients.
Options Considered
  • Direct Client-to-Agent WebSockets / REST: Exposes internal agents and allows unauthorized direct tool invocation bypassing backend authorization and audit logs.
  • Autonomous Multi-Agent Frameworks (LangChain / CrewAI loops): High runtime latency, unpredictable execution paths, and risk of unconstrained token consumption or loops.
  • Private Python FastAPI Service behind ASP.NET Core Gateway (Chosen): Secure facade pattern with strict role authorization, named tools, and webhook callbacks.
Decision Use a private Python service behind the ASP.NET Core Agent Gateway. The API owns authorization, workflow persistence, deterministic validation and approval; the agent returns structured proposals. Rejected: direct client-to-agent calls and uncontrolled tool access.
Consequences Benefits: Zero public exposure of AI ports; central JWT authorization and rate-limiting; guaranteed server-side validation; safe fallback when AI service is offline.
Trade-offs: Requires maintaining an inter-service contract between C# DTOs and Python Pydantic schemas via HTTP loopback.
Decision Summary: Use a private Python service behind the ASP.NET Core Agent Gateway. The API owns authorization, workflow persistence, deterministic validation and approval; the agent returns structured proposals. Rejected: direct client-to-agent calls and uncontrolled tool access.

ADR-04: Database Schema Strategy for Agent Workflow State

Field Details
Context Agent reasoning steps, fraud detection scores, quality inspection results, and admin approval decisions must survive server restarts, remain fully auditable for dispute resolution, and maintain referential integrity with related Catches, Bids, and Logistics records.
Options Considered
  • In-Memory / Local Cache State (Redis / Process Memory): Ephemeral; state is completely lost upon service restarts or container redeployments.
  • Unstructured NoSQL / Document Store (MongoDB): Lacks foreign key constraints and transactional integrity with the core relational business schema.
  • Relational Workflow Entity in PostgreSQL via EF Core (Chosen): Explicit relational tables (AgentWorkflows, LogisticsPlans) linked directly to business entities.
Decision Persist workflow identity, current agent, step status, validation, errors, approval and outcome in relational database records linked to the business entity. This supports auditability and recovery better than in-memory-only state.
Consequences Benefits: Guaranteed ACID persistence; complete audit trail of agent evaluations; administrative approval statuses survive deployment cycles; seamless SQL analytics.
Trade-offs: Requires explicit EF Core schema migrations whenever new agent metadata fields are introduced.
Decision Summary: Persist workflow identity, current agent, step status, validation, errors, approval and outcome in relational database records linked to the business entity. This supports auditability and recovery better than in-memory-only state.

ADR-05: Cloud Deployment Platform

Field Details
Context The multi-tier system (React web, ASP.NET Core API, Python Agentic AI microservice, Python Price API, and PostgreSQL) must be deployable to cloud infrastructure with reproducible continuous deployment, public SSL/TLS endpoints, and private internal networking for background agents.
Options Considered
  • Full AWS / Azure Cloud Infrastructure (ECS / App Service / RDS): High monthly operational cost, complex IAM policies, and excessive setup overhead.
  • Single Monolithic VM (DigitalOcean / EC2): Difficult to isolate microservices; manual Docker orchestration and SSL renewal required.
  • Render Cloud Platform with Managed PostgreSQL (Neon/Supabase) (Chosen): Blueprint-driven (render.yaml) infrastructure with automated builds and private networking.
Decision Target Render for API/client deployment with managed PostgreSQL through Neon or Supabase, using Dockerfiles and render.yaml. This is a deployment target, not verified evidence; add URLs only after a successful deployment and HTTP checks.
Consequences Benefits: Declarative infrastructure-as-code via render.yaml; built-in automated Git CI/CD; automated HTTPS/SSL; private service isolation for internal AI agents.
Trade-offs: Free/entry-level tiers may exhibit cold-start latency after inactivity; managed via keep-alive pings or upgraded instance configurations.
Decision Summary: Target Render for API/client deployment with managed PostgreSQL through Neon or Supabase, using Dockerfiles and render.yaml. This is a deployment target, not verified evidence; add URLs only after a successful deployment and HTTP checks.
