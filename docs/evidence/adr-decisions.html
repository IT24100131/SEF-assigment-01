ADR-01: React State-Management Approach

Field Details
Context The FishLink web dashboard requires managing multi-role UI states (Fisherman, Buyer, Admin, Logistics), JWT token persistence, dynamic live-bidding updates, and API loading/error feedback without overcomplicating frontend architecture or degrading browser rendering performance.
Options Considered
  • Redux Toolkit / Zustand: High architectural overhead, extensive boilerplate, and unnecessary complexity for a focused single-page role dashboard.
  • Global React Context: Triggers excessive re-renders across unrelated sibling components during high-frequency polling and real-time bid updates.
  • Route-level state with shared Axios client (Chosen): Lightweight, modular, and cleanly decoupled by feature and role view boundaries.
Decision Use React route-level state with a shared Axios API client and protected routing. Authentication identity and tokens are centralized with Axios interceptors and localStorage, while view-specific transactional data (catches, bids, logistics schedules) is managed locally within each dashboard component.
Consequences Benefits: Minimal bundle size (~130 KB), lightning-fast production compilation, zero global boilerplate, and centralized error/token expiration handling.
Trade-offs: Cross-screen data sharing requires re-fetching from the authoritative backend API or route params, preserving backend data integrity.
Decision Summary: Use React route-level state with a shared Axios API client and protected routing. This keeps the implementation simple while centralizing authentication headers, loading states and API errors. Rejected: duplicating business rules in each page.

ADR-02: Flutter State-Management Approach

Field Details
Context The mobile application requires managing offline session tokens, device hardware integrations (Camera for quality inspection, GPS for harbor geolocation), multi-step catch registration forms, and real-time buyer bidding while guaranteeing high UI responsiveness and minimal battery/memory footprint on Android and Web.
Options Considered
  • BLoC / Cubit: Excessive boilerplate (events, states, streams) for simple form flows and harbor operations.
  • Provider / Riverpod: Added external package dependency and potential version incompatibility risks with newer Flutter SDK releases.
  • Feature-oriented StatefulWidget + ApiService + FlutterSecureStorage (Chosen): Idiomatic Flutter pattern utilizing native widget lifecycles and dedicated service layers.
Decision Use feature-oriented StatefulWidget with local setState for UI reactions, combined with a modular ApiService for HTTP REST communication and FlutterSecureStorage for encrypted JWT persistence. Hardware sensor data (GPS, camera) is validated locally before dispatching to the API.
Consequences Benefits: Zero external state library overhead, maximum runtime performance, fast hot reload, and secure encrypted credential storage on iOS/Android.
Trade-offs: Deeply nested widgets pass callbacks explicitly, which was mitigated by keeping screen widget hierarchies modular and self-contained.
Decision Summary: Use feature-oriented StatefulWidget with a modular ApiService and FlutterSecureStorage. This provides native performance, instant hot-reloading, and secure offline token encryption without heavy external state dependencies. Rejected: bloated BLoC architecture for standard transactional screens.
